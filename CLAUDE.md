# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Lex Talionis** is a Fire Emblem fangame engine (pygame runtime) plus **LT-maker**, a PyQt5 graphical editor built on top of it. A game is a `.ltproj` directory of JSON data + resources; the engine loads one and plays it, the editor mutates one. The sample project `default.ltproj` (Sacred Stones) ships in-repo.

## Commands

- Run the editor: `python run_editor.py`
- Run the engine on a project: `python run_engine.py` (auto-finds a `*.ltproj` in the repo root)
- Run the map maker: `python run_map_maker.py`
- Run all tests: `python utilities/build_tools/run_tests_parallel.py` — every test module, spread over 8 processes (about 30s, against a few minutes serially). Arguments filter by module name (`run_tests_parallel.py save combat`), `-j N` sets the process count, `--slowest N` lists the slow modules, `--slow` also runs the slow tests (those skipped unless `LT_SLOW_TESTS` is set). Only failing modules print their output.
- Run all tests serially: `python -m unittest discover -s app/tests -p 'test*.py'` (wrapper: `./utilities/build_tools/run_tests.sh`)
- Run one test module: `python -m unittest app.tests.test_engine`
- Build docs: `./docs/make.bat html` (output in `_build/html`)
- Install dev deps: `pip install -r requirements_dev.txt` (engine-only: `requirements_engine.txt`, editor: `requirements_editor.txt`, CI tests: `requirements_test.txt`). Python 3.12 + PyQt5 + pygame-ce 2.5, the same Python and pygame-ce the browser build runs.
- Build the browser version: `python utilities/build_tools/build_web.py [project.ltproj] [--zip]`, the same build as the editor's File > Export for Web (`app/utilities/web_export.py`; no pygbag needed, it fills in a vendored copy of pygbag's page, `app/web/pygbag_default.tmpl`). Output in `build/web/<project>/`; `utilities/build_tools/web/serve.py` serves it to a phone on the local network. The page's own files (`main.py`, `page.js`) live in `app/web/`, so a release editor ships them.

`LT_PROFILE=1` env var enables per-frame timing prints in `driver.py`; `LT_PROFILE_THRESHOLD=<ms>` only prints slow frames. `LT_FRAME_STATS=1` prints a summary (`LTPERF`) every 120 frames instead.

The browser build (`sys.platform == 'emscripten'`) cannot start threads (`app/utilities/threads.py` runs work in place there), opens deferred music, sounds and battle sheets through `app/engine/deferred_files.load`, which has the file in place only while it loads it, and runs the main loop one frame per call (`driver.MainLoop.run_frame`, paced by `run_async`).

## Codegen

`app/engine/item_system.py`, `app/engine/skill_system.py` and the event command Python wrappers are **generated** (`app/engine/codegen/source_generator.py`) — never hand-edit them; edit the inputs and rerun `python -m app.engine.codegen.source_generator`. Details in `app/engine/CLAUDE.md`.

## Architecture

Three top-level halves under `app/`:

- **`app/engine/`** — the runtime game (pygame). Entry: `driver.start()` then `driver.run(game)`, a fixed loop pulling input → `game.state.update()` → blit. The whole game is a singleton `GameState` (`game_state.py`) holding every registry (units, items, skills, regions, parties, teams, vars). Control flow is a **stack-based state machine** (`state_machine.py`, `state.py`); states are registered by string nid in `StateMachine.load_states` and pushed/popped (`game.state.change/back`). Combat lives in `app/engine/combat/` driven by a `solver` producing a `playback` log that map/animation combat replay. Live game objects are in `app/engine/objects/` (UnitObject, ItemObject, SkillObject, etc.) — these wrap the static DB prefabs with per-playthrough state.

- **`app/data/`** — the project data model and (de)serialization. Two global singletons: `DB` (`app/data/database/database.py`) for game design data and `RESOURCES` (`app/data/resources/resources.py`) for assets. Both `.load(path, version)` a `.ltproj`. On-disk format is versioned JSON; migration logic is in `app/data/serialization/` (`versions.py`, `migrators/`, `loaders/`). `CURRENT_SERIALIZATION_VERSION` gates load behavior. Validation in `app/data/validation/`; a project with `has_fatal_errors` refuses to launch.

- **`app/editor/`** — PyQt5 editor. One sub-package per data type (e.g. `item_editor/`, `class_editor/`, `event_editor/`), each typically a `*_tab.py` (Qt view), `*_model.py` (Qt model over the DB), and `*_properties.py` (the edit form). `main_editor.py` is the window. Editor state lives in `app/editor/lib/state_editor/`. The editor edits `DB`/`RESOURCES` in memory and serializes back to the `.ltproj`.

Also: **`app/events/`** — the eventing/scripting system, including a custom Python-eventing compiler under `app/events/python_eventing/` (analyzer → compiler → postcomp) that turns user event scripts into runnable code. Event triggers are defined in `app/events/triggers.py` (chapter start/end, unit death, talk, level up, etc.) and matched against `EventPrefab.triggers` at runtime. **`app/map_maker/`** — a separate procedural tile-map tool, with its own palette pipeline (see `app/map_maker/README.md`). Its undo history (`map_history.py`) keeps, like the editor's, only the parts of the map's saved form each step changed (`app/utilities/form_diff.py`, shared with `edit_history.py`); every edit in the map maker window commits as it ends (a stroke on mouse release), and `MapPrefab.restore_in_place` redraws only the tiles an undo reaches. Each tile may be drawn with a palette of its own (palette fields, `palette_fields.py`: several palettes spreading from origins and blending into each other), so a renderer is handed the palette at each call (`palette_at`, in `qt_palette.py` and `pygame_palette.py`) and keeps one only for its terrain's icon; a blended palette draws its shape palette's sprites recolored through color maps voted from the sheets' pixels at the same places (`palette_blending.py`), blended in Oklab. **`app/engine/roam/`** — a free-roam exploration mode (town menus, NPC interactions) that runs as its own state machine alongside but separate from tactical map states; **`app/engine/overworld/`** — the node-based overworld graph (map selection, cinematics, route branching).

Subsystem notes live next to the code — read the relevant one before changing that area:

- `app/engine/CLAUDE.md` — codegen, component system and hook resolution policies, save/restart slots and `StaleSaveError`, auras, LTCache invalidation, fog of war / sight
- `app/engine/combat/CLAUDE.md` — combat cleanup phase ordering (`cleanup_combat` vs `end_combat`)
- `app/tests/CLAUDE.md` — `EngineTestCase` / `EngineHarness`, global-state and sprite leaks between tests, headless Qt

## Conventions

- **Every field of every database record is in `app/data/database/reference_schema.py`**: a `Ref` saying what it names, or `NOT_REF`. `references.py` walks the database by that schema; the editor logs a warning on project load, and `test_references.py` fails, on a field the schema leaves out. Editors rename and delete through `HISTORY.rewrite` / `reference_dialogs.check_delete`, never by walking the database by hand. A reference with `on_clear=REMOVE_RECORD` takes the record holding it along with the deletion (a level's events go with the level), and `check_delete` lists those and clears whatever names them too. A new prefab field means a new entry there; a list whose elements each name a different record (tags, an affinity's bonus per support rank) is `unique=True`, so a deletion swapping onto a record it already names drops the element rather than repeating the record. Event scripts are text the schema does not cover, and renames and deletions never change them: `app/events/event_references.find_mentions` finds the lines naming a record (certain when a command argument of that kind holds it, "may name it" when a quoted string does), a deletion's warning lists them in an Events tab, and after a rename the main window shows them in a `RenameWarning` that waits for no answer. `DBChecker.validate_references` reports every reference that names nothing as a warning, except the ones its own checks already report as errors (`CHECKED_REFERENCES`); `validate_resource_references` warns the same way of references the schema does not cover, between resources (combat animations' palettes, effects and sounds; tilemaps' tilesets and terrain), which each resource model renames and deletes by hand. The sample projects validate with no warnings at all.
- **Editor edits go through the undo history in `app/editor/edit_history.py`**, not whole-database snapshots. A tab binds the record it shows (`HISTORY.bind`, after the form shows it); catalog membership is diffed on every commit. A record's undo step keeps only the parts of its saved form that changed (a stroke on a tilemap, the tiles it painted), and undo patches the record's form as it is now, so it relies on the record being as the step left it; a resource with files keeps whole versions, which `keep_files` repoints. Code that changes records nobody has bound wraps the change in `HISTORY.modifying(...)`; run the editor with `LT_EDITOR_CHECK=1` to log any change that slipped past. There is one linear history for every window: Ctrl+Z in any editor window, or Undo in the main window, undoes the last change wherever it was made; in a text field with typing of its own to undo, Ctrl+Z undoes that first, and held down it stops once that runs out: only a fresh press goes on to the history. Undo and redo say what they changed, from the change set's deltas (`HISTORY.describe`: its label unless that is the plain `'Edit'`, else the records changed and their catalog): the main window's Undo and Redo menu items name the step they would take (and are greyed out with none), and an `UndoFeedback` label (in the main window's status bar, beside an editor window's Close) names the step just taken for a few seconds. An editor window has only Close, which keeps its edits; a picker run modal to choose a record has OK and Cancel, and Cancel only chooses nothing. An ID box never writes the record's nid as the user types: it renames when editing finishes, through the tab's `attempt_change_nid` or `HISTORY.rename` (record, cascade and copied name as one undo step) — a nid that disagrees with its catalog key, if anything commits meanwhile, records a rename without its cascade. Each change set, undo and redo is announced to `HISTORY.listen` listeners: an open dialog calls `reset()` on the tab it shows, unless that tab made the change, once the event that made it is done (its other tabs reset when switched to), and the main window resyncs the level editor. A change that only edits fields of levels, overworlds or tilemaps (`data_editor.map_catalogs`, what every click on a map changes; no rename, addition or removal) resets only the tabs whose `reads_maps` is set and whose `reads_map_edit(change_set)` says the change is one they read: the Tilemaps tab, and the Events tab when it changes the shown event's level, that level's tilemap or any overworld; `test_editor_show`'s `MapReadsTests` fails on a tab that reads one of those records while it resets, shows its records or draws without setting it, and under `LT_EDITOR_CHECK=1` a tab that skipped a reset resets anyway and logs whether that changed what it showed. The main window's level and overworld editors bind the level and overworld they show; the main window commits when focus moves within, into or out of it, and each click or key press that edits a map commits too, so each is an undo step of its own and never joins another window's edit. The main window does not show again a change its own views made. Resource manifest records are recorded the same way; a resource's saved form leaves out where its files are, so the history keeps the attributes its `path_fields` names beside it. Resource dialogs write nothing to the project: an import, or an editor that changes a file's bytes, puts the files in staging (`STAGING` in `app/editor/file_manager/staging.py`, never the project folder or beside the file the user chose) and points the record at them, and a staged file is never overwritten, so a new version gets a new path that undo can point away from. A project save copies files in and repoints the records, which the history takes as its new baseline rather than an edit, and autosave writes the resources from memory without repointing them. Before a save copies or overwrites a project file, or Remove Unused Resources deletes one, `HISTORY.keep_files` stages it and points every resource and every version in the history that uses it at the copy. The combat animation and effect editors stage a weapon animation's or effect's sprite sheet whenever they build or recolor one (`stage_full_image`); a frame set's pixmap never differs from the file it points at. A tab's `reset()` finds its shown record again (or a neighbour, if it was deleted), refreshes its `ObjBox`es and calls `set_current`; a combo box filled once in a form's `__init__` goes stale. Showing a record writes nothing to it: a form's handlers listen for the user's changes (`textEdited`, `activated`, a `MultiSelectComboBox`'s `updated`) or are blocked while `set_current` fills the widgets, since a write on show (a reordered list, `''` for `None`, a size fitted to a missing picture) is never recorded and so never undone. `test_editor_show.py` opens every editor window the main window opens and shows every record of every tab, and fails on any change to the database or any undo step (on `default.ltproj` too with `--slow`), and `test_main_window_show.py` does the same through the main window's global, level and overworld editors, in a process of its own, since the main window holds on to the edit history's listeners and the timer (`main_window_harness.py` opens it for such scripts); a repair of old data belongs where the project loads, before `HISTORY.clear()`, as fonts' palettes are pinned. `test_two_windows.py` edits in several windows in random order and checks that undoing everything gives back the database it started from (a slow test: run it with `--slow` after changing a form or the history). A widget that animates listens through `timer.connect_tick(widget, slot)`, which passes the tick on only while the widget is on show and its window is the active one (a slot does nothing a hidden widget needs: it catches up on the first tick once shown), never through `tick_elapsed` directly: a closed dialog's listeners would otherwise redraw for the rest of the session. A view passes itself as `origin=` for edits it already shows, so they don't redraw it under the cursor; focus moving to another window commits with the tab holding the field that lost it as origin (`EditHistoryDialog.tab_holding`), whichever window hears of the move first. The tilemap and tileset terrain editors run modal with an `EditSession` (`edit_history.py`): each stroke or menu action is an undo step, their Ctrl+Z reaches only the steps since they opened, and like every editor window they have only Close, after which each step stays in the history. The main window opens the editors on the history as windows beside it, not blocking it, through `EditorWindows` (`app/editor/editor_windows.py`): one window per maker, brought to the front if already open, deleted once closed, and all closed when a project loads or the editor quits. An editor tab's `edit()` returns its window unshown; pickers that return a choice still run modal. So do the list dialogs over a catalog (tags, game vars, translations, equations, weapon and support ranks), which are `RecordedListDialog`s (`app/editor/recorded_list_dialog.py`): they bind every record they list, so each edit is an undo step of its own, announced to the open windows. The movement cost grid is compared at every commit like a catalog's members, and renaming or deleting one of its movement types goes through the references like a record's nid. Save, Save As, New, Open, quit and test play first end the edit in the focused field, in the main window or an editor window (`MainEditor.finish_editing`), and the save and autosave progress dialogs block every window, since each step of their progress handles the events waiting.
- Objects are referenced by string ids: **NID** (named id, design-time, stable across a project) and **UID** (unique id, runtime instance). Types in `app/utilities/typing.py`.
- Shared, framework-agnostic helpers live in `app/utilities/` (no Qt, no pygame deps) — prefer reusing `utils.py`, `str_utils.py`, `static_random.py` (deterministic RNG for turnwheel/replays) over rolling your own.
- The engine must stay importable without PyQt5 (it ships as a standalone executable); keep editor-only imports out of `app/engine`.
- A MAJOR_FEATURES DB constant (e.g. `support`, `fatigue`) is usually **not** the runtime gate — it enables the feature in the editor/UI. The actual runtime switch is a `_`-prefixed game var (`_supports`, `_fatigue`, `_convoy`, `_turnwheel`) set via an event command (e.g. `game_var;_supports;True`), often deliberately deferred to a story beat. When gating engine behavior on a feature, check the game var, and check it in **every** path (combat, info menu, accumulation, etc.) — a missing check in one path leaks the feature inconsistently.
- Tests live in `app/tests/`, mostly engine/data/event coverage (the editor is largely untested). **Tests cover engine and editor code only, never a particular game's content or rules** — a game's own events and data are checked by hand or a throwaway script, not in this suite. The full suite takes minutes: while iterating, run only the test modules for what changed (`python utilities/build_tools/run_tests_parallel.py test_x test_y`) and run everything once before a commit. Several tests load the sample `.ltproj`s, so don't break their data integrity (`test_base_project_integrity.py`). Read `app/tests/CLAUDE.md` before writing a test or a headless engine/editor script.
